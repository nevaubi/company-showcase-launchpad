# ABS-EE: asset-level data of asset-backed securities

- Source: Form ABS-EE and ABS-EE/A on EDGAR, exhibit EX-102 (the asset data file, XML). Two callers share one reader (`filing.ts`): the scheduled job `abs-ee` (`src/lib/jobs/abs-ee.server.ts`) stores one waiting filing per run for the CIKs in `watch.ts`, or lists one of them when none waits; `scripts/abs-ee.ts` lists (`discover`, which asks SEC for the listing again on every run: a copy on disk is used only with `--offline`), stores oldest first in bounded batches (`load`), re-reads stored filings from SEC and compares (`verify`) and prints totals (`status`) for any CIK and range, with no time or size limit. History, and any file too large for a scheduled run, go through the script.
- The scheduled run reports failure only when the database or the code fails. A filing it cannot read is recorded on the filing (`status`, `status_detail`). An attempt is counted once, when the filing is claimed (`abs_claim_next`), and given back when SEC throttles or is down (`abs_release_filing`); a failure adds its reason without counting again (`abs_fail_claimed`), so a filing gets three real tries and is then left alone until someone looks. A file over the run's size limit (`ABS_JOB_FILE_LIMIT`) is not a failure: the filing is set aside as `skipped` with the reason, the job never claims it again, and `scripts/abs-ee.ts load --retry-skipped` stores it. Least-tried filings go first, so one stuck filing never holds up the rest. Scheduled before migration 0067 is applied, the run does nothing and says so. It is not in the freshness page's expected-cadence list (`SOURCES`): add it there only once its schedule exists and has run cleanly, or the watchdog reports it silent.
- Evidence kept with every stored filing: accession, form, filing and acceptance time, the cover period and the issuer, depositor and sponsor CIKs from the EDGAR header, the document list, and the size and SHA-256 of the asset file's bytes as SEC served them (`abs_filings`, `abs_documents`, `abs_loads`). A figure can be traced to the file, and the file checked against its hash.
- Values are stored as filed. A column holds the number, date or yes/no the text spells; text that does not spell one leaves the column empty and is kept word for word in `unparsed`; a field with no column is kept word for word in `extra`. Nothing is rescaled or corrected: some files write a rate as 0.0343 and others as 3.89, so a rate figure carries the unit `as_filed` until a per-file scale is established from the file itself.
- Two periods exist and are not the same thing: the cover period of the filing (EDGAR header, `abs_filings.period_start/period_end`) and the reporting period each record states (`period_begin/period_end` on the record). A file made for an offering is dated to a determination date that can lie after its filing date. Keep both; say which one a figure uses.
- Identity. A deal is the issuing entity: the header's filer that is not the depositor, keyed by its CIK as ten digits (`dealOf`); a filing whose only filer is the depositor is keyed by depositor CIK and file number; a header that establishes neither is not stored. `asset_number` is the filer's own number: unique within one file in the files seen, not stable across a deal's files (the offering file and the monthly files may number differently, a loan split into notes appears as 3, 3A, 3B, a property of a multi-property loan as 26-001 or 9.01). Rows are keyed by position in the file (`rec`). `classifyRecords` decides with the whole file in view: a row numbered after a loan in the same file that states no balance or payment status of its own is a property of that loan, even when it carries an amount (an offering file puts the loan amount allocated to each property on these rows, and counting them as loans counts that money twice); a numbered row with a balance of its own is a loan (a note of a split loan); a row no loan number fits stays untied, never guessed. What the file-wide look could not settle is kept with the load (`abs_loads.counts.notes`).
- The header's asset class is the filer's label: a header may list several, and one has been seen wrong ("Auto loans" on a commercial mortgage trust). It is stored as filed on the filing; what a deal is (`abs_deals.family`) comes from the namespace of its asset files, and a file of another family is refused for that deal rather than changing it.
- No company attribution. The tables hold SEC CIKs for issuer, depositor and sponsor and names as filed. Saying that a pool belongs to, or is a risk of, a covered company needs its own evidence (legal role at the time, retained interest) and is not derived from a name.
- Revisions are kept. An amendment is its own filing with its own rows. Among the loaded filings of one deal and one cover period, the one SEC accepted last is `is_current`; the others point at it (`superseded_by`). Nothing is overwritten. The tie is by cover period, and an amendment does not always keep the period of the filing it replaces: one was filed to change the reporting period itself (AXDB 2026-MULT1, 0001539497-26-002722 replacing 0001539497-26-002699: other dates in the header and in every record). Such an amendment is current for its own period and the filing it replaced stays current for the old one; `abs_review()` lists every amendment that shares its period with no other filing, and `status` prints them. Which filing an amendment replaces is stated only in the text of its cover page, which is not read yet: do not build a deal's time series across a period on that list without looking.
- Storing is all or nothing per filing: rows go under a new load (`abs_begin_load`, `abs_put_rows`) and become the filing's data only when `abs_commit_load` has counted them against what the reader parsed. A run can be stopped anywhere; the next run starts a cut-off filing over. A filing already stored from the same bytes by the same reader version is not stored again. Readers use the `*_live` views, which show only committed loads of loaded filings.
- The importer holds no SQL. Everything it does to the database is one of the service-role functions of migration 0067, called through `scripts/lib/abs-store.ts`. Do not write `abs_*` tables from anywhere else. `abs_check()` lists the store's invariants; every count must be zero after every run.
- Figures (`abs_pool_metrics`) are defined in `metrics.ts`; `PARSER` is bumped whenever a reader or a definition changes what gets stored, and `abs_loads.parser` records which version stored each filing (`abs-1` commercial mortgage only; `abs-2` adds auto loans and leases and stores a commercial mortgage file exactly as `abs-1` did). Every figure carries `n` and `n_missing`. Sums and weighted averages use exact decimal arithmetic (`decimal.ts`), so the same file gives the same figure on every run.
- Auto figures, and what they refuse to do. A filer omits an element instead of leaving it empty: a missing amount is counted in `n_missing`, never added as zero. Negative amounts are summed as filed. Weighted averages weigh by the end balance (loans) or end securitization value (leases) over records with an amount above zero, so they differ in the fourth decimal from a spreadsheet that weighs every record. A credit score counts only as a number from 300 to 900 (0, 9999 and "None" are placeholders; Ford's commercial scores run 1 to 299). `paymentToIncomePercentage` is never averaged and never divided by 100: Capital One and Nissan write percent points (8.73), others fractions (0.0873), and fraction files hold a few values above 100; it is stored as quantiles of the values as written plus the count above 1. State and make are grouped by their trimmed upper-case text; spelling variants of a make are not merged. Totals are of the records in the file: a file lists paid-off and charged-off loans too, and `original_balance` is not the deal's balance at closing. Nothing here says whether a file is an offering-stage pool or a monthly report: that is not stored yet.
- Read today, by the namespace of the file itself: commercial mortgage files (`cmbs`) record by record; auto loan and auto lease files (`auto.ts`) as pool figures only. One auto deal's monthly file holds 8,000 to 120,000 records in 30 to 380 MB, so the records are not stored: the filing, its documents with the file's size and SHA-256, and the figures in `abs_pool_metrics` are, and the file stays on EDGAR. They are read in one streaming pass with flat memory (the 52 files of the lineage work, 7.07 GB, peak 84 MB). The scheduled job cannot store them (size limit); the script does. A file of any other class is `skipped` with the reason "unsupported".
- The asset file reader (`xml.ts`) refuses a document it does not understand (deeper nesting, text beside elements, another root) instead of reading half of it. It was checked record for record against an independent parser on real files.
- Tests: pure modules beside them; the store's rules on a real PostgreSQL in `src/test/abs-store.db.test.ts` (set `ABS_DB_URL` to a scratch database on this machine); the SEC file source in `src/test/abs-source.test.ts`. The auto figures are checked against `src/test/fixtures/abs/auto-excerpt-figures.json`, computed from the same excerpts by another program. To prove a change end to end, apply the migration to a scratch Postgres and run the importer with `ABS_DB_URL` set; `ABS_FAULT=<begin|put|commit>:<n>` kills the process at that point of the n-th filing.
